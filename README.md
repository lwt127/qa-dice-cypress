# Joy Dice — QA Automation Assessment

A Cypress + TypeScript end-to-end suite for the Joy Dice game. It runs against the real launcher page
(https://qa-assessment-dice.play.purejoy.games/) and drives the game inside its iframe, the same way a casino embeds it.

## Install and run

Requires Node 18+ and Chrome or Electron (Electron ships with Cypress).

```bash
npm ci                      # installs Cypress 13 + TypeScript
npx cypress install         # only if your npm blocks postinstall scripts
npm test                    # full suite, headless Electron
npm run test:chrome         # full suite in Chrome
npm run cy:open             # interactive runner
npm run test:3x             # 3 consecutive runs -> runs/run-{1,2,3}.txt, runs/reports/run-{1,2,3}.html, runs/summary.txt
npm run screenshots:bugs    # reproduce every bug and save annotated screenshots -> docs/screenshots/
npm run typecheck           # tsc --noEmit
```

**Expected result today: 27 tests, 22 pass, 5 fail.** The 5 failures are the tests for BUG-002 to BUG-006 in
[`BUGS.md`](BUGS.md). Their titles end in `[BUG-00x]`, and they are meant to fail until those bugs are fixed.
BUG-001 was fixed in a redeploy around 2026-11-24 00:50. Its three Seed B tests were the ones that caught it, and they
now run as normal regression tests (earlier logs showed 19 passing and 8 failing for that reason).
BUG-007 and BUG-008 came from exploratory testing afterwards. They're reproduced by the screenshot spec, not yet by the regression suite.
To run only the regression gate (the 22 tests, all green), skip the known-bug tests:

```bash
npx cypress run --env skipKnownBugs=true
```

> Windows PowerShell: if `npm` is blocked by the execution policy, use `npm.cmd` / `npx.cmd`.

Only Chromium browsers are supported. The game iframe is on another origin
(`dev-games.cbet.cf.cvl.joystudios.xyz`), so the config sets `chromeWebSecurity: false`, which Firefox and WebKit don't honour.

## What is tested, and why

| Spec | Brief item | What it proves |
|---|---|---|
| `01-seeded-results.cy.ts` | 1. Results are correct | **Seed A, Over 98.00:** win, win, loss, loss; every roll value, win/loss state, history entry and exact balance (3,000 → 3,727.56 → 4,455.12 → 4,440.12 → 4,425.12). **Seed A, Under 50.00:** the same rolls give the opposite outcomes, so rolls don't depend on the target. **New visit:** balance and roll sequence reset. **Seed B:** the 50.00 boundary at Over 50, Under 50 and Over 40. These caught BUG-001, then confirmed its fix. |
| `02-recalculation.cy.ts` | 2. Win chance & multiplier | Over and Under; the target typed up and down across the full range; −/+ steppers; direction toggle; back-solving from win chance and from multiplier; clamping at both ends of each range. Checks the multiplier field, the "×N on Win" headline and the "Profits on Win (N×)" label agree. |
| `03-bet-balance.cy.ts` | 3. My choice: bet & balance integrity | The 1/2, 2x and chip buttons; capping at the balance; the 0.01 minimum; settlement exact to 4 decimals on small and odd bets; a fast double-click places exactly one bet; a bet bigger than the balance is blocked and recovers; an all-in loss goes to exactly 0 and blocks further bets; the displayed profit. |

**Why bet & balance integrity (item 3):** for a casino game, the costliest failure is the wallet being wrong:
taking or paying the wrong amount, accepting a stake the player can't cover, or placing a bet they didn't mean
to. Specs 01 and 02 prove the maths; this one proves the money that follows from it.

**How I decide what's "correct":** [`cypress/support/oracle/diceMath.ts`](cypress/support/oracle/diceMath.ts)
implements the rules from the brief independently of the UI, using integer and BigInt maths (10,001 rolls;
multiplier = 0.99 ÷ exact chance, cut to 5 significant digits; money in 0.0001 units). It's anchored to the brief's worked
example (Over 50.00 → ×1.9801) before anything else runs. Expected values are never read back from the screen, and
the key final balances are also written out as hand-calculated literals, so an oracle bug can't make both sides agree.

**Values chosen for recalculation:** both ends of each range (Over 2.00 / 99.99, Under 0.01 / 98.00), the midpoint
50.00, the default 50.50, values that move up then down in one session (to catch stale recalculation), and
non-round values (33.33, 12.34, 66.67). The multiplier must match exactly, because it's what the player is paid.
Win chance is compared to the exact probability within one display step (0.01). A separate strict test checks the
2-decimal rounding itself, because that's where the game is wrong (BUG-005).

**Deliberately not tested:** Auto-bet, hotkeys, sound/lightning toggles, the Provably Fair dialog and visual layout.
They matter, but in a 2–3 hour budget they come after "does the money come out right". I also didn't sweep
every target in Cypress (it's slow). I swept 854 targets once during exploration, which is how BUG-003 and BUG-004
were found, and kept representative values plus regression cases in the suite.

## Framework design

```
cypress.config.ts            baseUrl, chromeWebSecurity:false, retries OFF, timeouts
cypress/
  e2e/                       specs (one per brief item)
  fixtures/seeds.json        seeds, rolls, starting balance and bet: the single source of test data
  support/
    e2e.ts                   global hooks: stub third-party telemetry (Sentry, watson, Cloudflare)
    commands.ts              cy.openGame(seed): fresh player -> pick game -> pick seed -> Play -> ready
    knownBug.ts              knownBug('BUG-00x')(title, fn): run (and fail) or skip known-bug tests
    pages/LauncherPage.ts    launcher + seed dialog
    pages/DicePage.ts        the game inside the iframe: locators + actions (setTarget, placeBet, ...)
    oracle/diceMath.ts       independent maths/money oracle
    annotate.ts              evidence screenshots (red boxes + labels) and trusted CDP click/key input
  evidence/bug-evidence.cy.ts  reproduces each bug and screenshots it (not part of the regression run)
scripts/run-3x.js            N consecutive runs with logs
docs/screenshots/            generated bug screenshots, embedded in BUGS.md
```

How it stays reliable:

- **A fresh player per test.** Every test calls `cy.openGame()`, a new visit, so the balance is 3,000 and rolls restart. No test depends on another, and they can run in any order.
- **No fixed sleeps.** `placeBet()` waits for the game's own end-of-round signals: a new Previous Results entry and Bet re-enabled. Every assertion uses `should()` callbacks so Cypress retries until the UI settles.
- **Stable selectors.** In order of preference: the game's `data-test-id` hooks (`dice-bet-button`, `footer-balance`, ...), then `<label for>` text (`Roll Over`, `Win Chance`), with CSS classes only for Previous Results, which has no hook. The iframe body is re-queried on every access, so Vue re-renders never leave a stale element.
- **Real user input.** Numbers are typed with select-all + type, then a native blur commits them, the same way a user tabs out. Cypress's `blur()` can't see focus inside a cross-origin iframe.
- **Exact money.** Balances are parsed into integer 0.0001 units and compared as formatted strings, so floating-point drift can't cause false passes or failures.
- **Telemetry stubbed, game traffic untouched.** Third-party analytics posts return 429s and add noise, so they're answered locally. Wallet, launch and game requests go to the real servers.
- **Retries are off.** A flaky test should fail, not be retried until it passes. The three recorded runs use the same settings.
- **Bugs are visible, not hidden.** Known-bug tests assert the correct behaviour and fail. The `skipKnownBugs` flag lets CI keep a green regression gate while a second, non-blocking CI job runs them, and it turns green once they're fixed.

## Reliability: three runs in a row

`npm run test:3x` runs the whole suite three times back to back, with no retries. For each run it saves the full
console output (`runs/run-N.txt`) and a self-contained HTML test report (`runs/reports/run-N.html`, mochawesome),
which shows every test with its duration and, for failures, the error. See [`runs/summary.txt`](runs/summary.txt)
for one line per run.

**Recorded result:** all three runs produced the same result on the same build. The same 22 tests pass and the same
5 known-bug tests fail (BUG-002 to BUG-006), with identical failure messages, and nothing is skipped. Logs from earlier
builds and from the debugging below are kept in [`runs/archive-pre-final/`](runs/archive-pre-final).

**The suite caught a fix.** BUG-001 (the critical Seed B freeze) failed in every run until about 00:50 on 2026-11-24,
then passed from the next run on, with no change to the tests. A manual retest confirmed the game had been fixed. I
then removed its `knownBug` markers so those tests now guard against a regression, and recorded these runs afterwards,
so all three come from the fixed build.

**Two flaky failures I found and fixed.** Both were in the same place, the wait for the game to finish loading. Neither
was hidden with retries, `force: true` or sleeps. Each time I fixed the cause and re-recorded all three runs.

1. **The loading overlay.** One run had a 9th failure: *"`cy.click()` failed because this element is being covered by
   `<div data-test-id="dice-loading">`"*. The game's "Loading game..." overlay stays on top for about 3 s, *while the
   Bet button already reports itself as enabled*. My readiness check only looked at the button. The same pass fixed a
   helper that turned the BUG-001 failure message into an unhelpful `$b.find is not a function`.
2. **A slow server.** A later set of runs was about 45% slower than before (≈11 min per run against ≈7.5 min). In one
   run a test's setup failed with *"expected '' to match /^\d[\d,]*\.\d{4}$/"*: the balance wasn't rendered within
   15 s. The failure screenshot showed it loaded moments later. Cypress then skipped the 3 tests after it. The cause
   was that I'd given game *loading*, which depends on the network, the same 15 s timeout as quick UI checks.

**The fix, in [`DicePage.waitUntilReady()`](cypress/support/pages/DicePage.ts):** one retried check that requires every
readiness condition to be true *at the same moment*: balance rendered, multiplier calculated, overlay gone, Bet enabled.
It gets its own 60 s budget for game loading, while ordinary UI assertions keep 15 s. A game that hasn't loaded after
60 s is a real availability failure worth reporting, not flakiness. The recorded runs below include both fixes.

## Wrap-up: if this went live next week and I had one more day

First, **the client/server state contract: what the player sees versus what the wallet did.** Exploratory testing
showed that BUG-001 (since fixed) wasn't a maths bug. The server settled the 50.00 round correctly and the client never applied it,
and in Auto mode the server kept taking bets while the screen showed an unchanged balance. That's the most dangerous
kind of defect for a casino game, because the player's view and the ledger disagree. And it means the client has
result-handling paths nobody has tested. With one more day, I'd add a check to every round in the suite: compare the
displayed balance, history and nonce with the in-game Bet History (the server's record) after each bet, and fail on
any difference. Then I'd use that check against the risky paths: reloading or closing mid-round, a slow or dropped
network between bet and result (delaying or failing the game's traffic with `cy.intercept`), two tabs on one session,
and Auto-bet runs of 50–100 rounds with stop-on-profit/loss. I'd also automate BUG-007 and BUG-008 (silent max-win
rejection, and the double-tap hotkey), because both are about bets the player didn't intend or didn't understand.

Second, **the maths at scale.** Provable fairness is already verified: the seeds and rolls match Cloudbet's published
algorithm (see BUGS.md › Exploratory testing). The remaining risk is the odds. I'd move the 854-target sweep from
exploration into a fast check over all 19,600 Over/Under targets against the oracle. That would measure exactly how
many targets BUG-003/004/005 affect, and confirm the advertised 99% RTP holds everywhere, which is what regulators
and operators audit. If there's time left, a mobile-viewport pass, because that's where most casino traffic is.

## AI tools used

- **GitHub Copilot (agent mode in VS Code, Claude model):** explored the live game with a browser tool to find
  selectors, behaviours and edge cases, which is how the `data-test-id` hooks, clamping rules and BUG-001/006 were found. It also
  drafted the framework, specs, oracle, run script, CI workflow and these docs, and ran the 854-value sweep that found
  BUG-003 to BUG-005. It also drove the exploratory session (provably-fair verification against Cloudbet's published
  algorithm, max-win cap, Auto bet, hotkeys) that found BUG-007/008 and narrowed BUG-001 to a client-side failure.
  It also built the screenshot spec. That's where an error of mine came to light: my manual session had already turned
  hotkeys on, so I'd reported them as "on by default". Reproducing BUG-008 from a clean profile showed they're off by
  default, and I corrected BUGS.md and lowered BUG-008's severity.
- **My own role:** I decided what to test and why, and the design principles (an independent oracle, no sleeps, no
  retries, visible bugs). I verified each bug by hand, checked the oracle's maths and the expected balances by hand,
  and reviewed every assertion against the brief. Where the AI's first version was wrong (for example, a test that
  used Cypress's synthetic `dblclick()` and reported a false "double bet"), I investigated with real mouse
  events and corrected the test and the bug report (see BUGS.md, N-1).

## Part 2

[`REVIEW.md`](REVIEW.md) is written as a pull-request review of the teammate's `dice-seeded.cy.ts`. The verdict is
**request changes**. Rather than judging the spec only by reading it, I ran it and then ran a *mutant*:
[`cypress/review/dice-seeded.mutant.cy.ts`](cypress/review/dice-seeded.mutant.cy.ts), the same spec with the target
set to 99.99 so that bets 1 and 2 lose. The mutant still passed 6/6, so "wins the first/second bet" can't tell a win
from a loss. The original also failed 1 run in 3 in its `before` hook, because of its fixed `cy.wait(3000)`. Neither
file is part of the regression run, which only picks up `cypress/e2e/`.
